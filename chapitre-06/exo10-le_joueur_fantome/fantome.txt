Coupure : 16791, 16792, 16815, 16830. Quatre coupures mesurees en millisecondes, sur quatre essais successifs. J'ai tue le processus client par kill moins neuf, puis attendu que le serveur detecte le silence. Le delai est d'environ 16.8 secondes a chaque fois, tres stable. C'est le timeout d'inactivite du framework, kNkTimeoutMs = 10000 millisecondes dans NkNetDefines.h ligne 166, plus le temps de detection par cycle de UpdateConnections.

Fermeture propre : 92. Le client appelle manager.Disconnect avant manager.Shutdown, avec un Sleep de 3 secondes entre les deux. Le FIN part, le serveur le recoit a NkConnection.cpp ligne 500, et declenche onPeerDisconnected avec un ecart de 92 millisecondes. C'est la vraie fermeture propre, dix fois plus rapide que la coupure brutale.
Patch necessaire pour obtenir cette mesure. Sans patch, le FIN est envoye en canal RELIABLE_ORDERED. Ce canal exige un ACK. Le client ferme son thread reseau avant que l'ACK ne revienne, donc le FIN n'est pas retransmis s'il est perdu, et le serveur ne le recoit jamais. J'ai verifie en lancant le test sans patch : aucun DISCONNECT n'apparait cote serveur, seul le timeout de 10 secondes plus tard. Pour obtenir la mesure de 92 ms, j'ai modifie NkConnection.cpp ligne 310, en remplacant NkNetChannel::NK_NET_CHANNEL_RELIABLE_ORDERED par NkNetChannel::NK_NET_CHANNEL_UNRELIABLE dans l'appel a mRUDP.Send du FIN. C'est le meme remede que pour l'exercice 9 : un message de controle court n'a pas besoin d'ACK, et la perte d'un FIN unique est compensee par le timeout d'inactivite cote serveur. Le patch est local, il n'est pas dans le framework. Un correcteur qui veut reproduire la mesure doit appliquer le meme changement, ou attendre une correction officielle du framework.
Note : un second onPeerDisconnected apparait 6 secondes plus tard, avec la raison Disconnected, parce que le timeout d'inactivite se declenche encore sur la connexion deja fermee. C'est un double appel du framework, a signaler. Le joueur a deja ete retire de la table au premier appel, donc le second ne change rien a l'etat. Il faudrait que le framework ne declenche plus onPeerDisconnected sur une connexion deja retiree.

Raison : deux raisons observees. Pour la fermeture propre, raison = Force disconnected, transmise par NkConnection::ForceDisconnect quand le FIN est recu (NkConnection.cpp ligne 335). Pour la coupure brutale, raison = Disconnected, transmise par NkConnectionManager::UpdateConnections (NkConnection.cpp ligne 1318). Le framework distingue donc bien les deux cas par la raison.

Table : avant coupure, la table contient un joueur. Pendant la coupure, le joueur reste dans la table jusqu'au timeout. Apres le timeout, le joueur est retire et la table revient a zero. Pour la fermeture propre, le joueur est retire en 92 millisecondes. Les logs complets montrent chaque ajout et chaque retrait. Extraits :

Fil : le fil qui appelle onPeerDisconnected est le fil reseau du manager. Je l'ai verifie par la mesure. Le programme affiche le thread id dans le main et dans les callbacks. Sur un essai, le main affiche thread = 126735098234688, et les callbacks affichent thread = 126735091004992. Les deux valeurs sont differentes, donc onPeerDisconnected n'est pas appele depuis le fil principal. C'est le fil cree par StartServer a NkConnection.cpp ligne 935, qui execute NetThreadLoop ligne 1207, qui appelle UpdateConnections ligne 1219, qui detecte les connexions deconnectees et declenche le callback lignes 1317 et 1318. Pour la fermeture propre, le FIN est traite dans DispatchPacket ligne 499, qui appelle ForceDisconnect ligne 335, toujours dans le meme fil reseau.
Ce que cela impose a la table : elle est modifiee depuis un fil qui n'est pas celui du programme principal, donc toute lecture ou ecriture concurrente doit etre protegee. Mon programme utilise std::map protege par un std::mutex, avec std::lock_guard dans chaque callback et dans la boucle serveur. La table n'est donc touchee que d'une facon sure.
